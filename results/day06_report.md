# День 6 — Надёжность, guardrails и обработка ошибок

## Результат

В многошаговый LLM pipeline добавлены два механизма восстановления:
повтор запроса при временной ошибке API и один fallback prompt при
невалидном ответе модели. Проверки подключены ко всем пяти LLM-этапам.
Если восстановление невозможно, ошибка относится к конкретному тексту,
а обработка остальных текстов продолжается.

Проверено 30 октября 2026 года: **195 тестов прошли**, Ruff, проверка
форматирования и ty прошли. До изменений в проекте проходили 164 теста;
добавлен 31 тестовый случай. Машиночитаемый результат полного прогона:
[day06_tests.xml](day06_tests.xml).

Проверки выполнялись локально с подставными ответами и исключениями API.
Внешние запросы, реальные платежи и проверка доступности провайдера
не выполнялись. `day05.json` сохранён как исторический результат.

## 1. Повтор временных ошибок API

Изменён `src/itg_llm/llm_client.py`.

Для одного вызова допускаются первоначальная попытка и максимум два
повтора. Паузы перед повторами — 0,5 и 1 секунда.

Повторяются:

- ошибки подключения `APIConnectionError`;
- таймаут `APITimeoutError`, который наследуется от ошибки подключения;
- HTTP 408, 409, 429;
- серверные ошибки HTTP 5xx.

Остальные HTTP-ошибки завершают вызов сразу. В частности, повтор
не исправит неверный ключ, отсутствие прав или некорректный запрос:
400, 401, 403, 404, 422 не повторяются.

Таймаут SDK установлен в 30 секунд. Это ограничение ожидания операций
SDK, а не общий дедлайн всего текста или пакетного прогона.
Встроенные повторы SDK отключены через `max_retries=0`: повторами
управляет один слой приложения.

После исчерпания попыток выбрасывается `LLMAPIError` с понятным
сообщением, например:

```text
LLM API failed after 3 attempt(s): HTTP 503
```

В сообщение не переносится тело ответа API. Таким образом, диагностический
текст провайдера с внутренними данными не копируется в результат обработки.
Пустой список `choices` преобразуется в пустую строку и далее обрабатывается
валидатором как плохой ответ модели.

## 2. Fallback prompt для плохих ответов

Создан `src/itg_llm/guardrails.py`.

Функция `complete_validated()` выполняет запрос и проверяет ответ.
Если ответ не прошёл проверку, выполняется ещё один запрос с fallback
prompt. В него входят:

- исходная задача и весь контекст этапа;
- конкретное сообщение о нарушении;
- JSON Schema ожидаемой Pydantic-модели;
- требование заново сформировать JSON со всеми обязательными ключами;
- лимит символов итогового ответа, если проверяется этап генерации.

Повторная попытка предусмотрена для пустого ответа, невалидного JSON,
отсутствующих ключей, неверных типов, неизвестных значений enum,
чрезмерного размера сырого ответа и превышения длины `final_answer`.

Ошибки API не считаются ошибками формата: их обрабатывает retry в клиенте.
Если API не восстановился, fallback prompt не запускается впустую.
Если второй ответ модели также невалиден, этап завершается читаемой
ошибкой `LLMOutputError`. Успешный результат из выдуманных значений
не создаётся.

Fallback подключён в `pipeline.py` к `extract`, `classify`, `build_fields`,
`answer` и `self_check`. Последовательность и смысл этих этапов сохранены.

## 3. Ограничения формата и длины

Сохранены JSON mode, Pydantic-валидация, проверка обязательных полей,
непустых строк и допустимых категорий. По-прежнему поддерживаются
JSON в code fence и нормализация написания меток категорий.

Дополнительно введены ограничения:

| Ограничение | Поведение |
|---|---|
| Максимум 2048 выходных токенов в API-запросе | Ограничивает генерацию; совместимый провайдер должен поддерживать `max_tokens` |
| Максимум 32 000 символов сырого ответа | Проверяется перед разбором JSON |
| Лимит `final_answer` выбранного маршрута | Строгая проверка после разбора JSON |
| Одна fallback-попытка на выполнение этапа | Исключает бесконечное восстановление |
| Два повтора API на один запрос | Ограничивает число сетевых попыток |

Лимиты итогового ответа: support и complaint — 450 символов,
sales — 220, feedback — 200, general_question — 350, news — 250,
other — 150. Ровно предельное число символов допускается.

Длинный ответ не обрезается автоматически: обрезка могла бы удалить
важную деталь или часть инструкции. Сначала модель получает возможность
сгенерировать более короткий ответ; при повторном нарушении сохраняется
ошибка.

Ограничения summary, числа ключевых мыслей, языка и стиля остаются
мягкими проверками `quality.py`. Они формируют `issues`.

## 4. Логи и работа при частичных сбоях

В логах отражаются ошибка валидации, номер попытки, включение fallback,
успешное восстановление, временная ошибка API, номер повтора, пауза
и окончательная ошибка.

Сохраняется существующая трассировка этапов в `steps`: результат и время
успешного этапа, выбор маршрута и доработка после self-check. Время этапа
включает восстановление внутри него. Отдельные неудачные попытки
фиксируются в логах, а не отдельными элементами `steps`.

`run()` уже изолировал ошибки отдельных текстов; новый механизм использует
эту границу. Невосстановимый сбой даёт запись с `error`, после чего
начинается следующий текст. Основной CLI сохраняет результаты и возвращает
код 1, если хотя бы один текст завершился ошибкой.

В `compare_routes.py` расширена обработка ошибок: сбой API при генерации
одного маршрута записывается для этого маршрута и не останавливает
следующие. Ошибка общих этапов 1–3 остаётся ошибкой всего сравнения.

Если самопроверка недоступна и retry/fallback исчерпаны, текст получает
ошибку. Непроверенный ответ не выдаётся за успешно завершённую цепочку.

## 5. Негативные сценарии

| Сценарий | Проверенное поведение |
|---|---|
| Пустая строка вместо ответа | Fallback возвращает валидный ответ, цепочка завершается |
| Обычный текст вместо JSON | Fallback исправляет формат |
| Оборванный JSON | Выполняется восстановление |
| Отсутствует `final_answer` | Схема выявляет пропуск, fallback восстанавливает поле |
| Число вместо строки | Ошибка типа приводит к fallback |
| Ответ длиной 451 при лимите 450 | Fallback формирует короткий ответ |
| Повторный слишком длинный ответ | Читаемая ошибка, без обрезки |
| Сырой ответ больше 32 000 символов | Отказ до JSON parsing, число попыток ограничено |
| Невалидный ответ extract/classify/fields/check | Fallback действует на каждом этапе |
| HTTP 408/409/429/500/503, затем успех | Запрос повторяется и возвращает результат |
| Постоянные connection error, timeout, HTTP 503 | Остановка после трёх попыток |
| HTTP 400/401/403/404/422 | Немедленная ошибка без retry |
| Некорректны обе попытки одного текста | Следующий текст пакета успешно обрабатывается |
| Невосстановимая ошибка API одного текста | Следующий текст пакета успешно обрабатывается |
| Пустой список `choices` | Пустой ответ передаётся в обычную проверку |

Основные тесты: `tests/test_guardrails.py` и `tests/test_llm_client.py`.
Существующие тесты pipeline, сравнения промптов и маршрутов обновлены:
для невосстановимого случая теперь подаются два плохих ответа подряд,
поскольку один плохой ответ уже может быть исправлен.

## 7. Воспроизведение проверки

```bash
uv run pytest -q tests/test_guardrails.py tests/test_llm_client.py
uv run pytest -q --junitxml=results/day06_tests.xml
make check
```

В этой сессии использованы исполняемые файлы установленного `.venv`:
`pytest`, `ruff check`, `ruff format --check`, `ty check`.
Это позволило проверить текущий код без установки зависимостей.

Для последующего реального прогона на примерах:

```bash
uv run itg-llm --output results/day06_live.json
```

Эта последняя команда вызывает настроенный API и в данной сессии
не запускалась. При нормальном ответе остаются 5 LLM-вызовов на текст
или 7 при смысловой доработке. Fallback и сетевые повторы могут увеличить
число запросов и время выполнения. Формальная валидность и прохождение
self-check не гарантируют фактическую правильность каждого ответа.
